### SUG-001 — Expose a binary-safe pkt-line codec

- Status: `proposed`
- Affected abapGit component: `zcl_abapgit_git_utils`, `zif_abapgit_git_transport`, and `src/git/v2`
- Reviewed upstream revision: `v1.134.0` ([tag](https://github.com/abapGit/abapGit/releases/tag/v1.134.0), commit `b4eb6c7`)
- Current integration difficulty: `zcl_abapgit_git_utils=>pkt_string` frames text, while response parsing is coupled to the transport implementation and SAP HTTP client. A server or protocol test consumer needs to duplicate binary-safe packet parsing.
- HitHub code complicated by it: planned `src/core/pkt_line` and Steps 5–6 Smart HTTP handlers
- Smallest proposed refactoring/API change: add a public packet type and `encode`/`decode` methods that accept and return `xstring` payloads, preserving `pkt_string` as a compatibility wrapper. The codec should represent flush, delimiter, and response-end packets explicitly and reject invalid lengths.
- Intended ABAP usage:

  ```abap
  DATA(lv_packet) = zcl_abapgit_git_pkt_line=>encode(
    iv_payload = lv_binary_payload ).
  DATA(lt_packets) = zcl_abapgit_git_pkt_line=>decode(
    iv_stream = lv_binary_stream ).
  ```

- Expected benefits: One tested framing implementation for abapGit protocol-v0/v1/v2 clients, packet-trace tests, and future Git integrations; downstream consumers can process binary payloads without depending on an HTTP client.
- Compatibility, release, and migration considerations: Keep existing `pkt_string` behavior and add the new API without changing wire output. Add unit vectors for text, binary, empty, flush, delimiter, and malformed packets before adoption.
- HitHub fallback: implement `ZHI_CL_GIT_PKT_LINE` behind the HitHub core protocol port.
- Upstream issue or pull request: none identified in the reviewed issue and pull-request search on 2026-08-27.
- First abapGit version containing the change: `unknown`

### SUG-002 — Separate Git object codecs from pack framing

- Status: `proposed`
- Affected abapGit component: `zcl_abapgit_git_pack` and `zif_abapgit_git_definitions`
- Reviewed upstream revision: `v1.134.0` ([tag](https://github.com/abapGit/abapGit/releases/tag/v1.134.0), commit `b4eb6c7`)
- Current integration difficulty: `zcl_abapgit_git_pack` combines pack parsing/emission with tree, commit, and annotated-tag encoding/decoding. Consumers that need loose-object or browser operations must depend on a pack-oriented class or copy object serialization logic.
- HitHub code complicated by it: planned `src/core/object_codec` and Steps 3–4 object/pack implementations
- Smallest proposed refactoring/API change: extract a public `zcl_abapgit_git_object` codec for blob, tree, commit, and tag payloads plus canonical object headers; make the existing pack class delegate to it while retaining its current public methods.
- Intended ABAP usage:

  ```abap
  DATA(lv_commit_data) = zcl_abapgit_git_object=>encode_commit(
    is_commit = ls_commit ).
  DATA(lv_object_id) = zcl_abapgit_git_object=>id(
    iv_type = 'commit'
    iv_data = lv_commit_data ).
  ```

- Expected benefits: Reusable, independently testable object-format behavior for clients, repository tools, browsers, and pack code; fewer copies of canonical tree ordering and commit/tag parsing.
- Compatibility, release, and migration considerations: Existing `zcl_abapgit_git_pack` methods remain source-compatible and delegate to the extracted implementation. No object bytes or IDs may change; release with golden vectors and retain aliases if public names are later adjusted.
- HitHub fallback: implement `ZHI_CL_GIT_OBJECT_CODEC` and compare every generated byte and ID against abapGit and native Git fixtures.
- Upstream issue or pull request: none identified in the reviewed issue and pull-request search on 2026-08-27.
- First abapGit version containing the change: `unknown`

### SUG-003 — Add optional resource limits to pack and delta decoding

- Status: `proposed`
- Affected abapGit component: `zcl_abapgit_git_pack` and `zcl_abapgit_git_delta`
- Reviewed upstream revision: `v1.134.0` ([tag](https://github.com/abapGit/abapGit/releases/tag/v1.134.0), commit `b4eb6c7`)
- Current integration difficulty: pack decoding currently exposes no caller-supplied policy for maximum pack bytes, object count, decompressed object size, or delta-chain depth. A caller processing an untrusted remote pack must wrap or duplicate parsing to enforce its own limits.
- HitHub code complicated by it: planned quarantine ingestion in Step 6 and pack limits in Step 4
- Smallest proposed refactoring/API change: add an optional immutable limits structure to `decode` and delta decoding, with the current behavior preserved when it is omitted. Fail before allocation or ref promotion when a limit is exceeded.
- Intended ABAP usage:

  ```abap
  DATA(ls_limits) = VALUE zcl_abapgit_git_pack=>ty_limits(
    max_objects = 100000
    max_object_bytes = 104857600
    max_delta_depth = 50 ).
  DATA(lt_objects) = zcl_abapgit_git_pack=>decode(
    iv_data = lv_pack
    is_limits = ls_limits ).
  ```

- Expected benefits: Safer abapGit pulls from untrusted servers, predictable memory use, and a standard policy seam for server-side and batch consumers without changing normal client behavior.
- Compatibility, release, and migration considerations: The limits are additive and default to the existing behavior for backward compatibility. Document whether limits cover compressed input, decompressed payloads, or both, and add negative tests for integer overflow, truncated deltas, and decompression bombs.
- HitHub fallback: enforce limits in `ZHI_CL_PACK_READER` before object promotion and keep the upstream decoder isolated behind the compression/hash ports.
- Upstream issue or pull request: none identified in the reviewed issue and pull-request search on 2026-08-27.
- First abapGit version containing the change: `unknown`
